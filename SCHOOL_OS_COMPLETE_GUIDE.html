1️⃣ Project Overview

School OS is a Phase-1 Read-Only CRM Dashboard for school management and operations.

What It Does:

📊 Data Central
Centralizes school data (students, parents, teachers, finances, attendance) from Airtable
👥 Role-Based Dashboards
Different views for Owner, Finance, Admin, Teachers, and Marketing teams
💰 Financial Tracking
Revenue, expenses, receivables, teacher pay, invoices in real-time
🎓 Admissions Pipeline
Lead tracking → Trial booking → Enrollment conversion
📍 Branch Management
Multi-branch support with per-branch scoping and access control
📈 Analytics & Reports
Channel performance, enrollment trends, attendance health

Key Characteristics:

  • ✅ Read-Only in Phase 1 - No create, update, or delete operations allowed
  • ✅ Deny-by-Default RBAC - Users only see what their role permits
  • ✅ Field-Level Redactions - Sensitive data (DOB, medical notes) hidden from unauthorized roles
  • ✅ Server-Side Branch Scoping - Data isolation enforced server-side, not frontend
  • ✅ Minors Protection - Kyrgyzstan Personal Data Law No. 97 compliance for student records
  • ✅ Audit Logging - Every dashboard access and data view is logged

- React renders dashboard
- Charts, KPIs, and tables populate
Step 8: Audit Log Entry
- Dashboard access recorded: who, when, which role

4️⃣ Data Model & Tier System

School OS organizes all data into 4 security tiers. Each role has access to specific tiers.

The 4 Data Tiers

🔴 Tier 1 - Financial/HQ (Most Sensitive)

Accounting ledgers, journal entries, financial records. Append-only once posted.

Table Data
Account Chart of accounts, account balances
JournalEntry Financial transactions
LedgerLine Posted ledger lines (read-only)
Vendor Supplier information
Expense Expense tracking
TeacherPay Teacher payment records

Roles: Owner only

🟠 Tier 2 - PII (Personally Identifiable Information)

Student & parent data. Highly regulated, field-level redactions apply.

Table Data
Student Name, DOB, contact, medical notes (redacted from teachers)
Parent Name, phone, email (limited visibility)
User Staff & teacher accounts
Payment Payment records & history
Invoice Billing & receivables
Enrollment Student enrollment records

Roles: Owner, Finance, Office Admin (branch-scoped)

🟣 Tier 3 - Operational

Day-to-day operations (classes, attendance, schedules).

Table Data
Term Academic calendar
ClassGroup Class information & enrollment
Session Individual class sessions
Attendance Attendance records
Lead Admissions leads
Trial Trial classes & booking

Roles: Owner, Office Admin, Teacher, SMM (branch-scoped)

🟢 Tier 4 - Reference (Least Sensitive)

Reference data: branches, courses, pricing (read-only).

Table Data
Branch School branches & locations
Course Course catalog
TuitionPlan Pricing & fee structure
ChannelPerformance Marketing channel metrics (T4-RO)

Roles: All roles

Branch Scoping

Most tables have a branchIds column. Access is enforced server-side:

// Example: Office Admin sees only their branch branchIds = ["branch_5"] (their branch) Query: SELECT * FROM Student WHERE branchIds contains "branch_5"

Exception: T1 tables (Finance) and some HQ-level tables don't have branchIds. Access is by role alone.

Session & Authorization

On every request after login:

  1. Read Session Cookie - Extract user ID from cookie
  2. Validate Session - Check session exists and is not expired
  3. Load User - Fetch user record from PostgreSQL
  4. Check Role - Verify user has required role
  5. Apply RBAC - Filter data based on role permissions
  6. Enforce Branch Scope - Limit to user's branches
  7. Audit Log - Record action in audit trail

6️⃣ Role-Based Access Control (RBAC)

School OS uses deny-by-default RBAC: if a role doesn't explicitly have access, it's denied.

7 Roles & Their Access

👑 Owner (Director/HQ)

Access: All tables, all tiers, all branches

Typical View: Finance console, full student records, payroll, all analytics

Restrictions: None (Phase 1 = read-only, but could write in later phases)

Owner READ: T1, T2, T3, T4 WRITE: None (Phase 1)

💰 Finance

Access: T1 (Financial) + limited T2 (Payments/Invoices)

Typical View: Ledger, journal entries, payments, receivables, vendor management

Restrictions: Student and parent data redacted (shown as *)

Finance READ: T1, T2 (payments) WRITE: None (Phase 1)

🏢 Office Admin

Access: T2, T3, T4 (own branch only)

Typical View: Students, enrollments, attendance, classes (own branch)

Restrictions: Own branch only. No T1 finance data. No payroll.

Office Admin READ: T2-T4 (branch-scoped) WRITE: None (Phase 1)

👨‍🏫 Teacher

Access: Own classes + limited T3 data

Typical View: Own class sessions, student attendance, grades

Restrictions: Student DOB, medical notes, parent contact, payment history all hidden

Teacher READ: T4, limited T3 WRITE: None (Phase 1)

📱 SMM (Social Media Manager / Marketer)

Access: T3, T4 (admissions & marketing)

Typical View: Lead pipeline, trial bookings, channel performance

Restrictions: Own branch only. No payments, no medical notes, no parent contact

SMM READ: T3, T4 (branch-scoped) WRITE: None (Phase 1)

🔧 Tech Admin

Access: Diagnostics only

Typical View: System health, schema diagnostics, logs

Restrictions: PII only visible via audited break-glass access

READ: Diagnostics

🚫 Cleaner

Access: None

Status: Cannot log in (not registered in auth store)

7️⃣ Key Workflows

Workflow 1: Admissions Pipeline

How a potential student becomes enrolled

1️⃣ Lead Created
Marketing team or admin creates a new lead in the system
Data: Name, contact info, interest, source/channel
2️⃣ Lead Qualified
SMM marks lead as "Qualified" or moves to "Trial Booking"
Channel Performance tracking begins
3️⃣ Trial Class Booked
Teacher or admin books a trial session
Event created in Trial table with date/time
4️⃣ Trial Attended
Student attends trial class
Trial marked with outcome: "Completed", "No Show", or "Cancelled"
5️⃣ Conversion Decision
If outcome is "Completed" → Lead converted to Enrollment
Enrollment record created, student added to ClassGroup
6️⃣ Enrollment Active
Student appears on class roster, attendance tracked
Invoice generated for tuition

Conversion Rates Tracked:

  • Lead → Trial Booking: 45 trials booked / 100 leads = 45%
  • Trial Booked → Trial Attended: 35 attended / 45 booked = 77.8%
  • Trial Attended → Enrolled: 30 enrolled / 35 attended = 85.7%
  • Overall Lead → Enrolled: 30 enrolled / 100 leads = 30%

Workflow 2: Payment & Invoicing

How tuition fees flow through the system

1️⃣ Invoice Created
When student enrolls, invoice generated for tuition
Status: "Draft" or "Sent"
2️⃣ Payment Expected
Parent/student expected to pay by due date
Receivables KPI tracks unpaid invoices
3️⃣ Payment Received
Admin logs payment (cash, bank transfer, card)
Payment record created with amount & date
4️⃣ Invoice Marked Paid
Invoice status changes to "Paid"
No longer counted as receivable
5️⃣ Ledger Entry
Financial team records in General Ledger:
Debit: Cash, Credit: Revenue

Financial Tracking:

  • Monthly Revenue: Sum of payments received this month
  • Receivables: Sum of unpaid invoices (not "Paid" or "Cancelled")
  • Net Profit: Total Revenue - Total Expenses

Workflow 3: Teacher Payroll

How teachers get paid

1️⃣ Teacher Hours Logged
Teachers log hours worked (classroom + prep)
Data tracked in TeacherHours table
2️⃣ Hours Reviewed
Admin or finance reviews and confirms hours
Status: "Pending" → "Confirmed"
3️⃣ Pay Calculated
System calculates pay: hours × hourly_rate
Stored in TeacherPay table
4️⃣ Payment Issued
Finance team transfers payment to teacher account
TeacherPay status: "Pending" → "Paid"
5️⃣ Audit Trail
Owner dashboard shows unpaid teacher payments as alert
Payroll Alerts KPI visible to owner only

Workflow 4: Attendance Tracking

How daily attendance is recorded

1️⃣ Session Scheduled
Teacher creates a class session with date/time
Stored in Session table
2️⃣ Students Enrolled
Students in this class are linked to ClassGroup
Expected attendees determined
3️⃣ Attendance Recorded
During/after class, teacher marks attendance
Status: "Present", "Absent", "Late", "Excused"
4️⃣ Health Dashboard
Attendance Health KPI: (Present Today) / (Total Attendance Today) × 100%
Shows percentage of students attending today
5️⃣ Reports & Trends
Analytics show attendance patterns per student/class
Alerts for chronic absenteeism

9️⃣ Complete Data Flow Example

Example: Owner Views Dashboard

1. Browser Request
Owner opens https://crm.navstar-education.com/dashboard
2. Session Validation
Next.js checks secure session cookie → validates owner is authenticated
3. Component Renders
React loads OwnerDashboardClient component
Calls useEffect() to fetch dashboard data
4. API Request
Sends: GET /api/owner/dashboard?branch=all
Browser includes session cookie in request
5. Backend Validation
API handler /app/api/owner/dashboard/route.ts receives request
• Validates session exists
• Confirms user = Owner
• Checks RBAC: owner ✅ allowed
• Sets effectiveBranchIds = all branches
6. Database Queries
Backend runs 15+ database queries in parallel:
SELECT COUNT(*) FROM Student WHERE status='active'
SELECT COUNT(*) FROM Enrollment WHERE status='active'
SELECT SUM(amount) FROM Payment WHERE date>=monthStart
SELECT SUM(amount) FROM Invoice WHERE status NOT IN ('Paid', 'Cancelled')
... (and 11 more)
7. Airtable Proxy Calls
For student/enrollment data from Airtable:
• Calls airtableProxy.ts with PAT token
• Uses READ-ONLY PAT (no write capability)
• Fetches records matching branchIds
• Caches if configured
8. Field Redaction
No redactions needed (owner sees everything)
For other roles, sensitive fields would be removed here
9. Response Assembly
API builds JSON response:

✨ Summary

School OS is a secure, role-based CRM dashboard that brings school operations into one place:

🎯 For Owners/Directors

Complete visibility into all operations, financials, and staff across all branches

💼 For Office Admins

Branch-level operations: students, enrollments, attendance, scheduling

📚 For Teachers

Access to own classes and students, attendance recording, no sensitive PII

📱 For Marketing/SMM

Admissions pipeline tracking, lead conversion analytics, channel performance

💰 For Finance

Full ledger access, journal entries, receivables, vendor management

Diagnostics and system health, break-glass access for troubleshooting
🔒 Security First: Every feature is built with deny-by-default RBAC, field-level redactions, server-side branch scoping, and complete audit logging. Minors are protected by law, and all access is traceable.

🌍 Multi-Tenant Ready: Multiple branches can operate independently with their own data, staff, and settings. Each user sees only what they're authorized for.
